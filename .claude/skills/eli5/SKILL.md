# ELI5 — 쉽게 설명하기

설명 대상(파일, 함수, 개념, 에러 메시지, PR, 커밋)을 받아서 **먼저 조사하고, 그 다음
쉬운 말로** 설명한다. 추측으로 설명하지 않는다.

## 1. 먼저 조사한다

- 대상이 이 저장소 안에 있으면 **반드시 실제 코드를 읽고** 설명한다.
  파일명이 모호하면 `grep`/`glob`으로 후보를 찾고, 여러 개면 어느 것인지 물어본다.
- 대상이 이 저장소의 스택(Next.js App Router, React 19, Supabase, Tailwind)과 관련된
  프레임워크 동작이면, 기억에 의존하지 말고 `node_modules/next/dist/docs/` 의 해당
  가이드를 먼저 읽는다. (이 프로젝트의 Next.js는 학습 데이터와 다를 수 있다 — AGENTS.md 참고)
- 에러 메시지면 스택 트레이스에서 **우리 코드에 해당하는 첫 줄**을 찾아 거기서 시작한다.

## 2. 이 순서로 설명한다

1. **한 줄 요약** — 전문 용어 0개. "이건 ○○할 때 ○○해주는 코드예요."
2. **비유** — 일상적인 비유 하나. 억지스러우면 넣지 말 것. 비유는 하나면 충분하다.
3. **실제로 일어나는 일** — 번호 매긴 3~6단계로 흐름을 적는다.
   데이터가 어디서 와서 어디로 가는지가 핵심이다.
4. **코드에서 보기** — `src/lib/actions.ts:42` 처럼 파일:줄 형식으로 짚어준다.
   길어야 5~10줄만 인용한다. 파일 전체를 붙여넣지 않는다.
5. **헷갈리기 쉬운 점** — 실제로 오해하기 쉬운 부분이 있을 때만. 없으면 생략한다.

## 3. 말투 규칙

- 사용자가 쓴 언어로 답한다 (한국어로 물으면 한국어로).
- 전문 용어를 처음 쓸 때는 괄호로 한 번 풀어준다:
  "서버 컴포넌트(브라우저가 아니라 서버에서만 실행되는 리액트 컴포넌트)".
- "간단히 말하면", "쉽게 말해서" 같은 군더더기 도입부를 반복하지 않는다.
- **아이한테 말하듯 하지 않는다.** ELI5는 "유치하게"가 아니라 "사전 지식 없이도
  따라올 수 있게"라는 뜻이다. 사용자를 무시하는 말투는 금물.
- 길이는 대상에 맞춘다. 함수 하나면 10줄 안쪽, 시스템 전체면 더 길어도 된다.
  요청하지 않은 개선 제안이나 리팩터링 계획은 붙이지 않는다.

## 4. 하지 말 것

- 조사 없이 일반론으로 때우기 (이 저장소가 실제로 어떻게 하는지가 질문의 핵심이다)
- 설명하면서 코드를 고치기 — 사용자가 고쳐달라고 하면 그때 고친다
- 모르는 걸 아는 척하기. 확실하지 않으면 "이 부분은 확인이 필요하다"고 적고,
  어디를 보면 알 수 있는지 알려준다

## 이 저장소 지도 (조사 출발점)

| 궁금한 것 | 볼 곳 |
| --- | --- |
| 페이지/라우팅 | `src/app/**/page.tsx` (App Router — 폴더 = URL) |
| 서버에서 실행되는 폼 처리 | `src/lib/actions.ts` (Server Actions) |
| DB 접근 | `src/lib/supabase-server.ts`, `src/lib/supabase-browser.ts` |
| 테이블 구조·권한(RLS) | `sql/schema.sql` + `sql/add_*.sql` (나중에 추가된 마이그레이션) |
| 로그인 세션 쿠키 갱신 | `src/middleware.ts` |
| 로그인 필수 페이지 차단 | 각 `page.tsx` 안에서 유저 확인 후 `redirect()` |
| 화면 조각 | `src/components/*.tsx` |
| 공용 상수 (카테고리·지역·테마) | `src/lib/categories.ts`, `regions.ts`, `theme.ts` |
| 프로젝트 방향·의사결정 | `STRATEGY.md`, `README.md` |
